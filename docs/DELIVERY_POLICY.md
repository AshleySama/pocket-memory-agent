# Pocket Memory 分阶段交付规则

生效：2026-10-21。依据用户对重复测试、逐项打包、人工评审过晚及交付不透明的反馈修订。

本文件规定今后的执行节奏，优先于旧总纲、路线图、协作手册中“每个优化都完整回归／性能比较／发布验收”的要求。旧记录用于追溯，不是自动恢复所有优化的授权；既有质量标准不因减少重复执行而降低。

## 1. 每轮只有一个可说明的目标

开工前简述：本轮解决哪些用户问题、修改边界、必要验证、人工参与点和停止条件。通常集中处理 1—3 个相关问题类型；不要把整个长期待办都当成当轮范围。

先区分：当前版本已复现、历史失败待复核、静态风险待验证、体验建议。不能把旧 P0 名称直接当作当前仍有 P0 的证据。核对用户所测 EXE、当前源码、资料和模型配置，说明版本差异，不预设用户用了旧版本。

同类问题连续两次修改仍失败时，暂停加补丁，归纳共同根因、影响范围和备选方案；不要自动扩大题库、换模型或启动另一个大工程。范围内的修复自行推进；新增目标先写入待办。

## 2. 按阶段验证

| 阶段 | 触发及必要检查 | 本阶段结束条件 |
| --- | --- | --- |
| 只读评估／文档／样式 | 查相应证据；文档检查链接，样式检查相关界面和交互 | 输出明确结论与局限；不启动模型、全量回归或构建 |
| 局部修复 | 原始失败＋同类代表变体＋相邻正例／反例；涉及 RAG 时包含真实 `/api/ask` 路径 | 问题类型的定向检查通过，记录尚未执行的检查；不称已发布 |
| 小批次稳定 | 受影响模块及跨模块代表场景；共享解析／检索主链改变时合并跑一次全单元回归；仅在相应行为受影响时做少量真实问答和引用界面核对 | 范围内问题达到约定目标，适用的人工抽评完成或明确标为待评 |
| 冻结发布候选 | 对最终输入执行必要的全量回归；RAG 改动执行既有冻结题集；按风险补导入、备份恢复、目标机性能等验收 | 无未处置的已确认发布阻断；已知限制和验证缺口明确 |
| 正式打包 | 用户要求发布或本轮已约定发布；复用同一候选已有检查，构建一次，包级冒烟及模型完整性核对 | 交付一个明确版本、变更清单、未解决项和人工验收入口 |

这些阶段可合并，避免重复运行同一检查。涉及共享主链、数据写入、迁移等高风险变更，可提前扩大相关回归；须说明触发原因，不能机械坚持只测几题。

只有代码、依赖、模型、数据、运行配置或相关环境改变，或出现新失败／不确定性时，才重复受影响的检查。发布时记录一次输入指纹；不要求每次文案修改重新计算大模型哈希。

已有测试通过且与构建输入一致时，使用现有 `scripts/build_release.ps1 -SkipTests` 避免构建脚本再次调用全套回归。不能用它跳过尚未执行或已失败的必要检查。构建输入或包级检查失败才需要修复后重建，说明原因。

性能只在性能目标、模型／检索开销或目标机风险相关时专项测量。小样本报告实际耗时与样本数，不用少数题声称可靠 P95。文档/UI 不相关变更不触发完整 RAG 测试。

## 3. 按成果和问题类型验收，人工评审前移

**2026-11-07 按任务验证更新：** 先区分问答、专题报告和界面，按受影响风险验证。问答检查事实、问项覆盖、引用语义与定位；报告检查成稿完整性、统计口径、来源、编辑持久化和实际导出；界面检查受影响流程和状态，优先回放已有响应。纯文档／界面／报告排版不默认触发模型生成或问答百题；混合改动触及共享检索、解析或存储时补相应保护。

需要整体问答质量结论时，使用本轮约定的固定分层套件，稳定后统一回归；小批题只负责定位与局部验证。题量、预算和门槛由当前任务决定，历史 10—12／24／100／200 题及历次生成时限不自动成为新的默认。变化输入须重新验证；当前入口已证明模型请求契约和证据身份映射未变的题，可复用历史原始模型输出，再经过当前后处理及引用检查，不能只因问题／资料相同就复用最终响应。标明新链路检查、复用和新生成，不能宣称整套均为本版新跑。公开题、真实开发题、合成夹具分别报告，不能以公开题或合成机制成功替代真实办公体验。不得改分母、删失败或边跑整套边逐题改提示。

历史追溯：2026-10-25 曾约定首套约 100 题（80 公开＋20 真实保护题）及当轮预算调整；该套件和结果仍供配对复用，其一次性授权不自动重启任务，也不适用于专题报告／界面验收。当前实现范围、正式替换与发布点遵从用户最新授权。

- 每个问题保留资料、提问、预期事实与出处、实际回答、引用位置、版本及结论。预期答案由资料得出，不能从模型回答倒推。
- 表格类至少选择同类实体、单／多字段、常见连接词／空格、真实不存在实体或字段、相邻行干扰的代表情况。按问题选择表头缺失、正文/OCR 冲突、多页签来源等样例，不机械展开所有组合。
- 查询理解、召回、证据、生成和定位分别归因。测试生产查询扩展与参数传递；辅助函数成功不能替代真实入口。
- 分开报告事实正确、问题覆盖、引用支持、打开原文位置。关键词命中、引用编号合法或支撑代理分数不能证明答案忠实。
- 早期提供与本轮风险相称的小份真实问答评审包，由 Codex 整理预期事实和出处；用户只需判断是否可用及业务歧义。没有固定 10—12 题要求，样例不能用于宣称总体准确率；报告和界面直接提供可打开成果及关键核对点，不套用问答评分表。
- 人工评审不必等到最终 EXE；稳定源码预览即可。用户未参与时可继续独立工程工作，明确 `待人工评审`，不能代填通过；用户明确选择先打测试包则记录缺口。
- 开发、验证与用户保留的盲测分开。已看过并用于修复的题不再称盲测；保留失败历史，不修改金标准或删除失败来提高成绩。
- 资料真实性单独验收：记录全文长度分布、文档数量、切片与最终上下文长度，字符与 token 分开。短构造资料保留作回归，不能仅凭 `long_document` 标签宣称长文能力；重复正文或多问题不计作多份独立资料。
- 真实导入与注入切片分开：占位文件加标准切片的夹具不能证明 PDF／Excel／OCR 解析通过。长材料需覆盖中段、尾段、跨段证据及相似主题干扰，长度以真实库分布为依据。
- 优先复用成熟任务与工具：参考 CheckList 成组行为测试、LongBench／CRUD-RAG 的长材料和多文档任务，必要时用 Ragas 辅助生成与评分；保留现有运行器，只做必要适配。数据许可、中文适配和本地模型调用配置先核实。调研与首批范围见 [复赛评分与评测改进](../deliverables/PocketMemory_复赛评分与RAG评测改进_2026-10-21.html)。

## 4. 严重性和停止条件

P0 用于已复现的数据破坏／跨库污染、关键工作流不可用、严重无依据事实或错误主体／金额／条件造成的误导等阻断问题；具体结合场景影响判断。缺项、保守拒答、引用体验通常按 P1 处理，核心任务因此完全不可用时可升为 P0。静态可疑路径先标“待验证”，不要假装已确认漏洞。

停止条件是“本轮承诺的用户场景和必要验证完成，遗留项清楚”，不是“所有长期问题清零”。不因找到一个新边角就不断扩展本轮。对未通过的人评或目标机验收保持待评，不用工程通过替代。

## 5. Agent、文档和成本

主线程负责范围、根因判断、整合与对用户解释。普通单点修复由一个实现者完成；需要时安排一个范围明确的独立复核。可并行的独立模块才增加实现者，并指定互不覆盖的文件范围。

子 Agent 使用足够且简短的上下文、明确产出及停止点；不能重复全局扫描，也不能自行另起全量评测或构建。全局只设一个测试／发布执行者。工作量、审计份数和 Agent 数量不是质量指标。

当前批次以一份报告为状态依据，`CODEX_HANDOFF.md` 只链接和简述，历史路线图不反复复制全文。只展示关键失败、差异及结果，原始长日志留文件。保留必要的失败与最终证据，不为归档数量复制整个目录。

本地 Python、单元测试和 GGUF 推理主要消耗本机资源；Codex 推理、长上下文、工具输出与并行 Agent 会消耗账号额度。没有账号明细时不虚构某轮 token 用量或节省比例。

每轮给用户说明：解决了什么、尚未解决什么、做了哪些必要验证、当前是源码预览还是新包、下一步需要怎样的人工反馈。
